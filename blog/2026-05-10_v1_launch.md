# Shipping ghostloop v1.0 — the agent loop, embodied

Two months ago I started a side project. Today it's `pip install ghostloop`,
v1.0.0, eleven releases, 333 tests, and Claude Desktop can drive a robot
through it.

This post is the launch note: what it is, why it exists, how the eleven
releases compounded, and what's next.

## What ghostloop is

ghostloop is the layer between an LLM and a robot.

Modern LLM agents have a clear shape: tool registry, fail-closed policy
gates, structured trace, paired-comparison eval. Modern robotics has
ROS 2 (middleware) and VLA models like OpenVLA / π0 / RT-2 (policies).
Nobody had wired the two together — a runtime where the LLM emits
high-level intents like `move_to(0.4, 0.2, 0.1)` or `pick("widget-7")`,
those intents flow through a real safety pipeline, the survivors execute
on a backend (sim or hardware), and every step is captured in a typed
trace that can be replayed, audited, scored, mined, counterfactually
replayed, or causally attributed.

That layer is ghostloop. The shape borrows from `GhostAgent` in
[GhostLM](https://github.com/joemunene-by/GhostLM), my from-scratch
cybersecurity language model. The novel piece is binding it to robot
primitives instead of CVE lookups, making the runtime backend-agnostic
so the same agent loop drives a `MockBackend` today, MuJoCo right now,
and ROS 2 / direct hardware later — and adding the *post-hoc analysis*
tier (counterfactual replay, causal attribution, LLM-as-judge,
property mining, adversarial fuzzing) that no other robotics framework
ships.

## What you can do with it

```bash
pip install ghostloop[mcp]
```

Then add this to Claude Desktop's config:

```json
{
  "mcpServers": {
    "ghostloop": {
      "command": "python3",
      "args": ["/path/to/ghostloop/examples/mcp_robot.py"],
      "env": { "GHOSTLOOP_PROFILE": "franka_arm" }
    }
  }
}
```

Restart Claude. New conversations get tools — `move_to`, `set_gripper`,
`scan`, `pick`, `place`, `state`, `recent_trace`. Prompt: *"Move to
(0.4, 0, 0.5), scan with radius 0.3, then move to (0.6, 0.2, 0.5)."*
Watch Claude reason about the task and call the tools in sequence.

Now ask it to move to (5, 0, 0.5) — outside the workspace.

```
status: blocked
gate: geofence
reason: target x=5 outside workspace [-0.6, 0.6]
```

The actuator never sees the command. The fail-closed pipeline rejected
it. Claude reads the structured rejection, adjusts, tries again.

That's the whole thesis — *the safety pipeline is upstream of every
backend*. Same pipeline gates a Mock backend, MuJoCo, PyBullet,
Gymnasium, ROS 2 on real hardware, or the RandomizedBackend wrapper for
sim-to-real training. Six backends, twelve gates, one consistent
shape.

## How the eleven releases compounded

I didn't plan v1.0 from day one. I shipped what felt like the
next-most-impactful piece in front of me, six days a week, for two
months. The releases stacked like this:

- **v0.1** — core abstractions (Intent / Primitive / Runtime / Trace), three policy gates, MockBackend. 23 tests.
- **v0.2** — MuJoCoBackend + LLMPolicy adapter + bench harness with Wilson 95% CIs + McNemar exact + Cohen's h.
- **v0.3** — PyBullet, async runtime, declarative properties, MCP server, scripted policies.
- **v0.4** — ForceCap + HITL gates, episode catalogue, MuJoCo Menagerie auto-clone (Franka / UR5e / Spot / Aloha / Allegro), replay/diff CLI.
- **v0.5** — VLAPolicy adapter, sensor primitives, OpenTelemetry, SQLite store, planner DSL.
- **v0.6** — fleet abstraction, FastAPI dashboard, LLMPlanner, RetryGate, observation buffer, property combinators.
- **v0.7** — GymnasiumBackend, CooldownGate + TimeWindowGate, convex polytope SDF, composite primitives, Mission DAG runner, WebSocket streaming.
- **v0.8** — STL temporal properties, URDF workspace builder, RandomizedBackend, trace query DSL, safe-RL harness with Lagrangian.
- **v0.9** — ROS2Backend, ActionSmoothingGate, safe-action projection, reward shaper DSL, Sim2RealBench.
- **v0.10** — counterfactual trace replay, causal failure attribution, LLM-as-judge, adversarial bench generator, property mining, skill graph, hindsight relabeling, energy ledger, cross-embodiment morphology registry.
- **v1.0** — RGB-D fusion + lightweight object detection, VLA-on-MuJoCo benchmark suite vs OpenVLA / π0 / RT-2 / Octo / Diffusion Policy / ACT, production fleet dashboard with auth + rate limit + alarms + Prometheus.

Then the post-v1.0 polish work that turned it from "research project"
into "thing you can pip-install":

- Cross-morphology primitive library (drive / sit / takeoff / wave / set_joint / sense — 26 primitives).
- RobotProfile system + YAML loader so non-developers can describe their own robot in 30 lines and ghostloop boots it.
- MCP server that works with every MCP-aware client (Claude Desktop / Cursor / Continue / Cline / Zed / Gemini CLI), every OS, every transport (stdio / streamable-http / sse).
- Direct OpenAI-compatible function calling for users who'd rather skip MCP entirely.

Eleven releases. 333 tests. ~7000 lines of Python. MIT.

## What was novel vs what was standard

The bench harness pattern (Wilson CIs + McNemar + Cohen's h paired
comparison) isn't novel — that's textbook. The runtime + safety
pipeline shape isn't novel either — it's how every modern LLM-agent
framework is built; I borrowed it from my own GhostLM.

What IS novel, as far as I can tell from the literature in 2026:

1. **Counterfactual trace replay for robotics.** Replay a recorded
   episode through a different policy and diff their decisions step
   by step. LLM safety teams do this routinely; robotics doesn't.
2. **Causal failure attribution.** Leave-one-out ablation over a
   failing trace to find which events were causally necessary for
   a property violation. Flame-graph for safety violations.
3. **LLM-as-judge for robot traces.** Pair-compare every recorded
   episode against a four-criterion rubric (task completion, safety,
   efficiency, recoverability). Free reward-modelling-quality eval.
4. **Property mining.** Auto-discover candidate invariants from a
   corpus of successful traces. Promote them to formal Property
   objects with one method call.
5. **Adversarial bench generator.** Random / grid / CMA-ES search
   over Episode initial states to find failure-prone seeds. Promote
   the worst into the regression bench.

Each of these is a known pattern in adjacent fields (LLM red-teaming,
formal verification, adaptive testing). None of them ship together in
any robotics framework I know of.

## What was hardest

The trace shape, weirdly. Every event has to carry: intent, decision
(allow / deny / escalate, with gate name and reason), result (status,
observation, message), state_before, state_after, timestamp. Get any
field wrong and counterfactual replay breaks, the property engine
returns spurious results, the LLM judge can't read the prompt.
Designing it right took three iterations across v0.1-v0.4.

The second-hardest piece was the conditional-import pattern. Six
backends, six install paths, six possible failure modes if you
import lazily wrong. Every backend constructor raises `ImportError`
with a specific install hint at construction time only — never at
package import. Test count went from 23 to 333 partly because every
new conditional-install case ships with an "is this gracefully
skipped if the lib isn't there?" test.

## What's next

I have three things on the roadmap:

1. **arXiv preprint on the post-hoc analysis tier.** Counterfactual
   replay + causal attribution + LLM-judge + property mining is a
   workshop paper writing itself.
2. **Real OpenVLA reproduction.** ghostloop ships the bench harness
   with published baseline numbers (`pick_place_widowx`,
   `manipulation_bridge`, `reach_target`). Running an actual
   OpenVLA-7B checkpoint through it and publishing the comparison
   would be a substantial validation.
3. **Live demo video.** Claude Desktop driving a Franka in MuJoCo
   through the safety pipeline, recorded as a 60-second hero. The
   work is done; the video is the catalyst that makes people *find*
   the work.

Ship dates: this month, this month, this month.
